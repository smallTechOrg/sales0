# Phase 2 — CRM memory + READ-ONLY Google Sheet sync + shared login
Implement spec/roadmap.md "Phase 2" (pipeline, contacts, timeline/follow-ups, signals, registries, import/paste, shared login; slices 2A-2H) with the NEW requirements below. Phase 1.4 (thorough discovery, seen_posts, linkedin_profiles, enquiries only for genuine) is already in the tree: build on it; prospects key off linkedin_profiles (unique slug). Accepting an enquiry upserts ONE prospect per linkedin_profile (idempotent), sets linkedin_profiles.tracked=true, links enquiry->prospect, writes a timeline event.

## Lifecycle (binding, user's words)
Enquiry/Prospect stages: New -> Contacted -> Follow-up 1 -> Follow-up 2 -> Final follow-up. Lead only after contact AND a response; Lead stages: Meeting scheduled -> Proposal sent -> Won / Lost / No response. Client = working with us + legacy clients. Contacts = shared people (email/phone/LinkedIn), taggable/categorisable, scalable to thousands, linked to everything. Competitors linked to enquiries/clients. Full timeline of every change; follow-up reminders ("Due today"); repeat-poster + competitor-mention flags.

## GOOGLE SHEET SYNC (new, critical) — ONE-WAY, READ-ONLY, SHEET IS SOURCE OF TRUTH
The app NEVER writes to Google Sheets (no write scopes, no write code; add a test that fails if any non-GET request to docs.google.com/sheets.googleapis.com is possible). It reads the sheets and upserts into the CRM.

- Mapping (record as Assumed and document in spec): Active Enquiries -> accepted enquiries + prospects (+ leads when Status/dates show a response: map statuses sensibly, keep the raw sheet Status in a `sheet_status` field); Discarded Enquiries -> discarded enquiries/seen_posts with reason; Outreach, Prospects, Working Sheet -> prospects (source tags) keyed by LinkedIn slug; Competitors -> competitors; Groups -> groups registry.
- Idempotent upsert by stable natural key: enquiries: normalized post URL else hash(email|requirement summary) else row hash; prospects: linkedin slug else email else name+company; competitors: normalized website else name; groups: link else name. Per-record `sheet_source` (sheet_id, gid, row_number, row_hash). Unchanged row_hash -> skip. Changed -> update only SHEET-OWNED fields; sheet wins conflicts; CRM-owned data (timeline, AI fields/verdicts, app notes, flags) preserved. Row disappears from the sheet -> set `sheet_removed_at` (soft; never hard-delete). Every sheet-driven create/update writes a timeline event (actor "sheet-sync").
- Robust parsing: dates without year (infer from Date Added / nearest past), multiple emails in a cell, phone normalisation, "Not provided"/"-" => null, blank/ragged rows, duplicate headers, header whitespace; bad rows are counted + reported per tab, never abort the sync.
- Job surfaces: `uv run python -m sales0.cli sync-sheets [--dry-run] [--tab NAME]`; Setup/Sync page "Sync now" + status panel (last sync, per-tab added/updated/unchanged/removed/errors, last error); in-process interval scheduler (env SALES0_SHEET_SYNC_MINUTES default 30, 0 disables; never overlaps itself; survives restarts; first run shortly after boot). Dry-run prints a diff summary only.
- Tests: synthetic CSV fixtures reproducing every quirk above; idempotency (sync twice = 0 changes); sheet edit propagates; removal soft-marks; CRM-owned fields survive; no-write test; fake HTTP transport (httpx MockTransport). LIVE gate: `sync-sheets --dry-run` against the two REAL sheets, read-only, printing ONLY per-tab row counts + parse-error counts (assert Active Enquiries > 0 rows); then (still read-only) a real sync into a TEMP db to prove the mapping end to end, counts only.
